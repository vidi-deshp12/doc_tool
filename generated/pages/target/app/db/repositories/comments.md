# comments

This module is the database access layer for comment-related operations in the application, defining a single class that handles all persistence work for comments [[target/app/db/repositories/comments.py]].

The class [`CommentsRepository`](target/app/db/repositories/comments.py) inherits from `BaseRepository`, which provides the underlying database connection infrastructure shared across all repository classes [[target/app/db/repositories/comments.py::CommentsRepository]]. Its constructor accepts an `asyncpg` `Connection`, passes it up to the base class, and also constructs a `ProfilesRepository` instance stored as `self._profiles_repo` using that same connection — making author profile resolution available throughout the class [[target/app/db/repositories/comments.py::CommentsRepository]].

The private async method [`_get_comment_from_db_record`](target/app/db/repositories/comments.py) is the single assembly point for `Comment` domain objects: it maps raw database fields (`id`, `body`, `created_at`, `updated_at`) from the returned row and awaits `self._profiles_repo.get_profile_by_username` to resolve the author's full profile before returning a fully constructed `Comment` [[target/app/db/repositories/comments.py::CommentsRepository]]. This helper has no side effects of its own and does not interact with the database directly — it is purely a hydration step [[target/app/db/repositories/comments.py::CommentsRepository]].

All four public methods delegate their SQL execution to the `queries` module and then rely on `_get_comment_from_db_record` to turn raw rows into domain objects [[target/app/db/repositories/comments.py::CommentsRepository]]. [`get_comment_by_id`](target/app/db/repositories/comments.py) fetches a single comment by integer ID scoped to a specific article's slug, and raises `EntityDoesNotExist` if no matching row is found [[target/app/db/repositories/comments.py::CommentsRepository]]. [`get_comments_for_article`](target/app/db/repositories/comments.py) retrieves all comments for an article by slug and hydrates each row through the shared helper, returning a `List[Comment]` [[target/app/db/repositories/comments.py::CommentsRepository]]. [`create_comment_for_article`](target/app/db/repositories/comments.py) persists a new comment via a SQL insert and converts the returned row into a fully hydrated `Comment` [[target/app/db/repositories/comments.py::CommentsRepository]]. [`delete_comment`](target/app/db/repositories/comments.py) is a thin pass-through that removes a comment by delegating to `queries.delete_comment_by_id` with the comment's `id_` and the author's username, returning `None` [[target/app/db/repositories/comments.py::CommentsRepository]].

### _get_comment_from_db_record

`_get_comment_from_db_record` is a private async helper on `CommentsRepository` that assembles a fully hydrated `Comment` domain object from raw database data [[target/app/db/repositories/comments.py::CommentsRepository::_get_comment_from_db_record]]. It accepts three keyword-only arguments beyond `self`: a `comment_row` of type `Record` holding the raw database row, an `author_username` string identifying the comment's author, and an optional `requested_user` of type `Optional[User]` representing the currently authenticated user, if any [[target/app/db/repositories/comments.py::CommentsRepository::_get_comment_from_db_record]].

The method constructs and returns a `Comment` instance by mapping fields directly from `comment_row` — specifically `id`, `body`, `created_at`, and `updated_at` — and by awaiting a call to `self._profiles_repo.get_profile_by_username` to resolve the author's full profile [[target/app/db/repositories/comments.py::CommentsRepository::_get_comment_from_db_record]]. The `requested_user` is forwarded to that profile lookup, allowing the profile repository to determine follow state or other viewer-relative data for the author [[target/app/db/repositories/comments.py::CommentsRepository::_get_comment_from_db_record]].

Because it delegates the profile fetch to a collaborating repository and must await the result, the method is declared `async` [[target/app/db/repositories/comments.py::CommentsRepository::_get_comment_from_db_record]]. It is a pure construction helper with no side effects of its own: it neither reads from nor writes to the database directly, instead relying entirely on the already-fetched `comment_row` and the injected profiles repository [[target/app/db/repositories/comments.py::CommentsRepository]].

### get_comments_for_article
