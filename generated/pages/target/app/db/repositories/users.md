# users

This module defines the data-access layer for user records in the application, exposing a single class that centralises every database operation involving users [[target/app/db/repositories/users.py]].

`UsersRepository` is that class, and it inherits from `BaseRepository`, which provides the shared `connection` attribute used in every method [[target/app/db/repositories/users.py::UsersRepository]]. It is not a model itself but works with the Pydantic models `User` and `UserInDB` as both inputs and return values, keeping the database layer clearly separated from the domain layer [[target/app/db/repositories/users.py::UsersRepository]].

The class exposes four async methods that together cover the full lifecycle of a user record [[target/app/db/repositories/users.py::UsersRepository]]. The two read methods, `get_user_by_email` and `get_user_by_username`, each delegate a lookup to the named query over `self.connection` and unpack the result into a `UserInDB`; when no matching row is found, both raise `EntityDoesNotExist` with a descriptive message rather than returning a silent `None`, making the absence of a user an explicit typed error [[target/app/db/repositories/users.py::UsersRepository]]. `create_user` accepts a plain-text password alongside `username` and `email`, constructs an in-memory `UserInDB`, and immediately calls `change_password` on it to derive the salt and hashed password before any SQL is issued; the insert runs inside an async transaction, and the method returns the in-memory object merged with the database row so that server-generated values such as the auto-assigned `id` are reflected in the result [[target/app/db/repositories/users.py::UsersRepository]]. `update_user` accepts the current `User` object and up to five optional keyword-only fields, re-fetches the authoritative record via `self.get_user_by_username` first, applies each non-`None` field using an `or`-fallback pattern, and, if a new password is provided, calls `change_password` to refresh the salt and hash; the SQL update is then executed atomically inside a transaction, and the server-returned `updated_at` timestamp is written directly onto the in-memory object before it is returned to the caller [[target/app/db/repositories/users.py::UsersRepository]].

## UsersRepository

`UsersRepository` is the data-access class responsible for all database operations involving user records [[target/app/db/repositories/users.py::UsersRepository]]. It inherits from `BaseRepository`, which supplies the shared `connection` attribute used throughout every method [[target/app/db/repositories/base.py::BaseRepository]]. The class is not a Pydantic model; it is a plain Python class that works with Pydantic models (`UserInDB`, `User`) as inputs and return values [[target/app/db/repositories/users.py::UsersRepository]].

The class exposes four async methods. `get_user_by_email` accepts a keyword-only `email: str` argument, delegates the lookup to `queries.get_user_by_email` over `self.connection`, and either returns the matching row unpacked into a `UserInDB` or raises `EntityDoesNotExist` if no row is found [[target/app/db/repositories/users.py::UsersRepository::get_user_by_email]]. `get_user_by_username` follows the same pattern keyed on `username: str`, raising `EntityDoesNotExist` with a descriptive message when no match exists, making the absence of a user an explicit typed error rather than a silent `None` [[target/app/db/repositories/users.py::UsersRepository::get_user_by_username]].

`create_user` takes `username`, `email`, and a plain-text `password` as keyword-only arguments and constructs an in-memory `UserInDB`, calling `change_password` on it immediately to derive and store the salt and hashed password before any SQL is issued [[target/app/db/repositories/users.py::UsersRepository::create_user]]. The insert runs inside an async transaction on `self.connection`, and the method returns `user.copy` merged with the database row so that server-generated values such as the auto-assigned `id` are reflected in the result [[target/app/db/repositories/users.py::UsersRepository::create_user]].

`update_user` accepts the current `User` object plus five optional keyword-only fields (`username`, `email`, `password`, `bio`, `image`), all defaulting to `None` so only the explicitly supplied values are changed [[target/app/db/repositories/users.py::UsersRepository::update_user]]. It first re-fetches the authoritative record via `self.get_user_by_username`, applies each non-password field with an `or`-fallback pattern, and, if a new password is provided, calls `change_password` to refresh the salt and hash before writing [[target/app/db/repositories/users.py::UsersRepository::update_user]]. The SQL update is executed atomically inside a transaction, and the server-returned `updated_at` timestamp is assigned directly onto the in-memory object, which is then returned to the caller [[target/app/db/repositories/users.py::UsersRepository::update_user]].

### create_user

`create_user` is an asynchronous method on `UsersRepository` that accepts a username, email, and plain-text password as keyword-only arguments and returns a `UserInDB` instance [[target/app/db/repositories/users.py::UsersRepository::create_user]]. It begins by constructing a `UserInDB` object with the supplied username and email, then immediately calls `change_password` on that object to hash the password and populate the `salt` and `hashed_password` fields before anything is persisted [[target/app/db/repositories/users.py::UsersRepository::create_user]]. The actual database insert is performed inside an async transaction opened on `self.connection`, where `queries.create_new_user` is awaited with the connection and the four user fields — `username`, `email`, `salt`, and `hashed_password` — returning a database row [[target/app/db/repositories/users.py::UsersRepository::create_user]]. The method finishes by calling `user.copy` with the row data merged in via `dict(user_row)`, so the returned `UserInDB` reflects any values the database may have set (such as an auto-generated `id`) while still carrying the in-memory state built earlier [[target/app/db/repositories/users.py::UsersRepository::create_user]]. Because the insert runs inside a transaction, any failure will roll back the write before the method returns [[target/app/db/repositories/users.py::UsersRepository::create_user]].

### get_user_by_email

`get_user_by_email` is an asynchronous method on the [`UsersRepository`](target/app/db/repositories/users.py::UsersRepository) class that retrieves a single user record from the database by their email address [[target/app/db/repositories/users.py::UsersRepository::get_user_by_email]]. It accepts a single keyword-only argument `email` of type `str` and returns a [`UserInDB`](target/app/db/repositories/users.py::UsersRepository::get_user_by_email) instance on success [[target/app/db/repositories/users.py::UsersRepository::get_user_by_email]].

The method delegates the actual database lookup to `queries.get_user_by_email`, passing `self.connection` along with the provided `email`, and awaits the result [[target/app/db/repositories/users.py::UsersRepository::get_user_by_email]]. If a matching row is returned, it is unpacked into a `UserInDB` object, which is then returned to the caller [[target/app/db/repositories/users.py::UsersRepository::get_user_by_email]]. When no matching row is found, the method raises [`EntityDoesNotExist`](target/app/db/errors.py::EntityDoesNotExist) with a message that includes the queried email address, signalling to upstream callers that no user with that email exists in the database [[target/app/db/errors.py::EntityDoesNotExist]] [[target/app/db/repositories/users.py::UsersRepository::get_user_by_email]].

> **Raises:** EntityDoesNotExist

### get_user_by_username

`get_user_by_username` is an asynchronous method on the [`UsersRepository`](target/app/db/repositories/users.py::UsersRepository) class that looks up a single user record by their username and returns it as a typed model [[target/app/db/repositories/users.py::UsersRepository::get_user_by_username]]. It accepts a single keyword-only argument, `username: str`, and returns a `UserInDB` instance on success [[target/app/db/repositories/users.py::UsersRepository::get_user_by_username]].

Internally, it delegates the database lookup to `queries.get_user_by_username`, passing the repository's active connection alongside the provided username [[target/app/db/repositories/users.py::UsersRepository::get_user_by_username]]. If a row is returned, the method constructs and returns a `UserInDB` by unpacking the row directly into its constructor [[target/app/db/repositories/users.py::UsersRepository::get_user_by_username]].

If no matching row is found, the method raises [`EntityDoesNotExist`](target/app/db/errors.py::EntityDoesNotExist) with a descriptive message that includes the missing username [[target/app/db/errors.py::EntityDoesNotExist]] [[target/app/db/repositories/users.py::UsersRepository::get_user_by_username]]. This makes the absence of a user an explicit, typed error rather than a silent `None` return, ensuring callers are forced to handle the not-found case [[target/app/db/errors.py::EntityDoesNotExist]].

> **Raises:** EntityDoesNotExist

### update_user

`update_user` is an asynchronous method on `UsersRepository` that applies partial updates to an existing user record and returns the updated state [[target/app/db/repositories/users.py::UsersRepository::update_user]].

It accepts the current `User` object as a mandatory keyword argument alongside five optional keyword-only fields — `username`, `email`, `password`, `bio`, and `image` — each defaulting to `None` so that only the values explicitly supplied by the caller are changed [[target/app/db/repositories/users.py::UsersRepository::update_user]]. The method begins by fetching the authoritative in-database representation of the user by calling `self.get_user_by_username` with the current username, giving it a fully populated `UserInDB` object to work from [[target/app/db/repositories/users.py::UsersRepository::update_user]]. Each of the four non-password fields is then updated with an `or`-fallback pattern: the new value is used when provided, and the existing database value is kept when it is `None` [[target/app/db/repositories/users.py::UsersRepository::update_user]]. If a new `password` was supplied, `user_in_db.change_password` is called to derive and store a fresh salt and hashed password on the in-memory object before any SQL is issued [[target/app/db/repositories/users.py::UsersRepository::update_user]].

The database write is executed inside a transaction opened via `self.connection.transaction()`, ensuring the update is atomic [[target/app/db/repositories/users.py::UsersRepository::update_user]]. Within that transaction, `queries.update_user_by_username` is awaited with the connection and all seven updatable column values — `new_username`, `new_email`, `new_salt`, `new_password`, `new_bio`, and `new_image` — and its return value (the new `updated_at` timestamp) is assigned directly onto `user_in_db.updated_at` [[target/app/db/repositories/users.py::UsersRepository::update_user]]. The method returns the mutated `UserInDB` instance, which now reflects every applied change including the server-side timestamp [[target/app/db/repositories/users.py::UsersRepository::update_user]].
