# users

The [`target/app/db/repositories/users.py`](target/app/db/repositories/users.py) module serves as the data-access layer for user records, providing all persistence operations — creation, lookup by email or username, and updates — through a single repository class [[target/app/db/repositories/users.py]]. It imports domain models `User` and `UserInDB`, the pre-compiled `queries` object, `BaseRepository` for connection management, and `EntityDoesNotExist` for signalling missing records [[target/app/db/repositories/users.py]].

The sole class defined here is `UsersRepository`, which inherits from `BaseRepository` and implements every database operation the application needs for user persistence [[target/app/db/repositories/users.py::UsersRepository]]. Creation is handled by `create_user`, which constructs a `UserInDB` in memory, hashes the password, executes an insert inside an explicit transaction via `queries.create_new_user`, and merges any database-generated values back onto the returned model so the caller always receives a fully populated record [[target/app/db/repositories/users.py::UsersRepository]]. Lookup is provided by two methods: `get_user_by_email` queries by email address and raises `EntityDoesNotExist` when no row matches, while `get_user_by_username` does the same keyed by username, both hydrating a successful result into a `UserInDB` instance [[target/app/db/repositories/users.py::UsersRepository]]. Finally, `update_user` ties the other methods together — it first fetches the current persisted state via `get_user_by_username`, selectively overwrites only the fields for which a new non-falsy value was supplied (`username`, `email`, `bio`, `image`), re-hashes the password through `change_password` when a new one is provided, and then flushes all changes inside a database transaction before returning the fully updated `UserInDB` to the caller [[target/app/db/repositories/users.py::UsersRepository]].

## UsersRepository

`UsersRepository` is a database repository class responsible for all persistence operations on user records, including creation, lookup, and update [[target/app/db/repositories/users.py::UsersRepository]]. It inherits from `BaseRepository`, which provides the underlying database connection management [[target/app/db/repositories/base.py::BaseRepository]]. It is not a Pydantic model.

The `create_user` method builds a new `UserInDB` instance from the supplied username and email, salts and hashes the password via `change_password`, then inserts the record inside an explicit transaction using `queries.create_new_user` [[target/app/db/repositories/users.py::UsersRepository::create_user]]. The resulting database row is merged back onto the in-memory model so that any database-generated values such as the assigned `id` are reflected in the returned object [[target/app/db/repositories/users.py::UsersRepository::create_user]].

The `get_user_by_email` method queries the database for a single row matching the given email address, hydrates it into a `UserInDB` model on success, and raises `EntityDoesNotExist` if no matching row is found [[target/app/db/repositories/users.py::UsersRepository::get_user_by_email]]. Similarly, `get_user_by_username` delegates to `queries.get_user_by_username` using the repository's active connection, returns a `UserInDB` when a row is found, and raises `EntityDoesNotExist` when the username is absent [[target/app/db/repositories/users.py::UsersRepository::get_user_by_username]].

The `update_user` method first fetches the current persisted state via `get_user_by_username`, then selectively applies only those optional fields — `username`, `email`, `bio`, `image` — for which a non-falsy value was provided, leaving the rest unchanged [[target/app/db/repositories/users.py::UsersRepository::update_user]]. When a new password is supplied, `change_password` is invoked to refresh the salt and hashed password before any write occurs [[target/app/db/repositories/users.py::UsersRepository::update_user]]. All writes are executed inside a database transaction, after which the fully updated `UserInDB` record is returned to the caller [[target/app/db/repositories/users.py::UsersRepository::update_user]].

### create_user

Async method on [`UsersRepository`](target/app/db/repositories/users.py::UsersRepository) that creates and persists a new user, returning a [`UserInDB`](target/app/db/repositories/users.py::UsersRepository::create_user) instance populated with the database-assigned fields. It first constructs a [`UserInDB`](target/app/db/repositories/users.py::UsersRepository::create_user) from the supplied `username` and `email`, then calls `change_password` to salt and hash the provided `password` before any database work begins [[target/app/db/repositories/users.py::UsersRepository::create_user]]. The insert is executed inside an explicit `self.connection.transaction()` block via `queries.create_new_user`, passing `username`, `email`, `salt`, and `hashed_password` derived from the model [[target/app/db/repositories/users.py::UsersRepository::create_user]]. The returned database row is merged back into the in-memory model with `user.copy(update=dict(user_row))`, so the caller receives a fully hydrated object that reflects any database-generated values such as the assigned `id` [[target/app/db/repositories/users.py::UsersRepository::create_user]].

### get_user_by_email

Fetches a single user record from the database by email address, delegating to the underlying query layer [[target/app/db/repositories/users.py::UsersRepository::get_user_by_email]]. When a matching row is found, it is hydrated into a `UserInDB` model and returned [[target/app/db/repositories/users.py::UsersRepository::get_user_by_email]]. If no row exists for the given email, it raises `EntityDoesNotExist` with a message identifying the missing address [[target/app/db/errors.py::EntityDoesNotExist]].

> **Raises:** EntityDoesNotExist

### get_user_by_username

Fetches a user record from the database by username, delegating the query to `queries.get_user_by_username` with the repository's active connection [[target/app/db/repositories/users.py::UsersRepository::get_user_by_username]]. When a matching row is found it constructs and returns a `UserInDB` instance from the raw row data [[target/app/db/repositories/users.py::UsersRepository::get_user_by_username]]. If no row is returned, it raises `EntityDoesNotExist` with a message identifying the missing username [[target/app/db/errors.py::EntityDoesNotExist]].

> **Raises:** EntityDoesNotExist

### update_user

Fetches the current persisted state of the user by delegating to `get_user_by_username` with the caller-supplied `user.username` [[target/app/db/repositories/users.py::UsersRepository::update_user]]. Each optional field (`username`, `email`, `bio`, `image`) is applied only when a non-falsy value is provided, leaving the existing value intact otherwise [[target/app/db/repositories/users.py::UsersRepository::update_user]]. When `password` is supplied, `change_password` is called on the fetched record to update the salt and hashed password before persisting [[target/app/db/repositories/users.py::UsersRepository::update_user]]. All writes are executed inside a database transaction opened via `self.connection.transaction()`, within which `queries.update_user_by_username` is called with the full set of (possibly unchanged) field values and its return value is stored as `user_in_db.updated_at` [[target/app/db/repositories/users.py::UsersRepository::update_user]]. The fully updated `UserInDB` record is returned to the caller [[target/app/db/repositories/users.py::UsersRepository::update_user]].
