# users

This module is the data-access layer for all user-related database operations in the application [[target/app/db/repositories/users.py]]. It defines a single class, `UsersRepository`, which inherits from `BaseRepository` and relies on the shared `connection` attribute that parent class supplies to every method [[target/app/db/repositories/users.py::UsersRepository]].

`UsersRepository` exposes four asynchronous methods that together cover the full lifecycle of a user record [[target/app/db/repositories/users.py::UsersRepository]]. `get_user_by_email` and `get_user_by_username` are lookup methods that each delegate to the `queries` layer, return a `UserInDB` instance on success, and raise `EntityDoesNotExist` with a descriptive message when no matching row is found [[target/app/db/repositories/users.py::UsersRepository]]. The two methods follow the same structural pattern, differing only in which field — email or username — drives the query [[target/app/db/repositories/users.py::UsersRepository]].

`create_user` accepts a `username`, `email`, and `password`, constructs a transient `UserInDB` object, hashes the password before any database interaction occurs, and inserts the record inside an atomic transaction [[target/app/db/repositories/users.py::UsersRepository]]. It returns the result of merging the freshly inserted row — including any server-generated values such as an auto-assigned id or timestamps — back onto the in-memory model [[target/app/db/repositories/users.py::UsersRepository]].

`update_user` takes an existing `User` object together with five optional keyword arguments — `username`, `email`, `password`, `bio`, and `image` — and applies selective updates to the stored record [[target/app/db/repositories/users.py::UsersRepository]]. It first fetches the current database state by calling `get_user_by_username` internally, then merges each provided field using a short-circuit `or` so that absent arguments leave stored values unchanged, and derives fresh salt and hash values if a new password is supplied [[target/app/db/repositories/users.py::UsersRepository]]. The entire write is wrapped in a transaction, and the timestamp returned by the underlying query is assigned directly to the in-memory object so it remains consistent with what was persisted [[target/app/db/repositories/users.py::UsersRepository]].

### create_user

`create_user` is an asynchronous method on `UsersRepository` that creates and persists a new user record, returning a fully populated `UserInDB` model [[target/app/db/repositories/users.py::UsersRepository::create_user]].

It accepts three keyword-only arguments — `username`, `email`, and `password` — all typed as `str`, and returns a `UserInDB` instance [[target/app/db/repositories/users.py::UsersRepository::create_user]].

The method begins by constructing a transient `UserInDB` object from the provided `username` and `email`, then immediately calls `user.change_password(password)` to derive and store a salt and hashed password on that object before anything touches the database [[target/app/db/repositories/users.py::UsersRepository::create_user]].

The actual insert is performed inside an `async with self.connection.transaction()` block, ensuring the write is atomic; within that block, `queries.create_new_user` is awaited with the connection plus the four derived fields — `username`, `email`, `salt`, and `hashed_password` [[target/app/db/repositories/users.py::UsersRepository::create_user]].

Finally, the method returns `user.copy(update=dict(user_row))`, merging the raw database row (which may contain server-generated values such as an auto-assigned `id` or timestamps) back onto the in-memory model to produce the definitive `UserInDB` return value [[target/app/db/repositories/users.py::UsersRepository::create_user]].

### update_user

`update_user` is an asynchronous method on [`UsersRepository`](target/app/db/repositories/users.py::UsersRepository) that applies selective updates to an existing user record and returns the fully updated user as a `UserInDB` [[target/app/db/repositories/users.py::UsersRepository::update_user]]. It accepts the current `User` object as a required keyword argument alongside five optional keyword-only fields — `username`, `email`, `password`, `bio`, and `image` — any subset of which may be provided to override the stored values [[target/app/db/repositories/users.py::UsersRepository::update_user]].

The method begins by fetching the user's current database state via `self.get_user_by_username`, using the username already held on the supplied `User` object [[target/app/db/repositories/users.py::UsersRepository::update_user]]. Each optional field is then merged with the existing value using a short-circuit `or`, so a `None` or absent argument simply leaves the stored field unchanged [[target/app/db/repositories/users.py::UsersRepository::update_user]]. When a new `password` is provided, `user_in_db.change_password` is called to derive and store fresh salt and hashed password values before the database write occurs [[target/app/db/repositories/users.py::UsersRepository::update_user]].

The actual persistence is wrapped in a database transaction opened through `self.connection.transaction()`, ensuring the write is atomic [[target/app/db/repositories/users.py::UsersRepository::update_user]]. Inside the transaction, `queries.update_user_by_username` is called with the connection and all resolved field values; its return value is assigned directly to `user_in_db.updated_at`, keeping the in-memory object consistent with what the database recorded [[target/app/db/repositories/users.py::UsersRepository::update_user]]. The fully updated `UserInDB` instance is then returned to the caller [[target/app/db/repositories/users.py::UsersRepository::update_user]].
