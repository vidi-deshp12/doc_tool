# articles

[`target/app/db/repositories/articles.py`](target/app/db/repositories/articles.py) is the data-access module for all article-related database operations, and it establishes a small set of module-level constants used across the repository [[target/app/db/repositories/articles.py]]. The string constants `AUTHOR_USERNAME_ALIAS` and `SLUG_ALIAS` name the column aliases expected in raw query results, while `CAMEL_OR_SNAKE_CASE_TO_WORDS` holds a regex pattern used for identifier parsing [[target/app/db/repositories/articles.py]].

The module's single class, `ArticlesRepository`, is the data-access class responsible for all database operations relating to articles, inheriting from `BaseRepository` [[target/app/db/repositories/articles.py::ArticlesRepository]]. Because it deliberately contains a higher-than-usual number of methods, it carries a `# noqa: WPS214` suppression [[target/app/db/repositories/articles.py::ArticlesRepository]]. On construction, it creates two collaborating repositories — a `ProfilesRepository` and a `TagsRepository` — both sharing the same database connection, so article-level operations can delegate profile and tag lookups without opening separate connections [[target/app/db/repositories/articles.py::ArticlesRepository]].

Two private helpers underpin the public interface. `_get_article_from_db_record` assembles a fully populated `Article` domain object from a raw database row, accepting `slug` and `author_username` as separate parameters, fetching the author profile with follow-state awareness, retrieving associated tags and favorites count, and resolving the `favorited` flag only when a `requested_user` is present [[target/app/db/repositories/articles.py::ArticlesRepository]]. `_link_article_with_tags` associates a sequence of tag strings with an article by slug, writing one mapping per tag through the query layer [[target/app/db/repositories/articles.py::ArticlesRepository]].

The write operations form a coherent group. `create_article` persists a new article and its tags atomically inside a transaction before hydrating and returning a full domain object [[target/app/db/repositories/articles.py::ArticlesRepository]]. `update_article` deep-copies the existing article, overlays any supplied field replacements, and executes the update within a transaction keyed by the original slug and author [[target/app/db/repositories/articles.py::ArticlesRepository]]. `delete_article` removes the article row within a transaction using the same slug-and-author-username key [[target/app/db/repositories/articles.py::ArticlesRepository]].

The read operations cover both single-record and collection lookups. `get_article_by_slug` fetches and hydrates one article, raising `EntityDoesNotExist` when no matching row is found [[target/app/db/repositories/articles.py::ArticlesRepository]]. `filter_articles` builds a dynamic pypika query that can optionally join on tags, author, or favorites, and returns a paginated, personalised list of hydrated `Article` objects [[target/app/db/repositories/articles.py::ArticlesRepository]]. `get_articles_for_user_feed` queries for articles written by authors the requesting user follows and hydrates each raw row before returning the list [[target/app/db/repositories/articles.py::ArticlesRepository]].

The remaining methods handle tag and favorites data as discrete concerns. `get_tags_for_article_by_slug` returns all tags for an article as a flat list of strings, and `get_favorites_count_for_article_by_slug` returns the integer count of users who have favorited a given article [[target/app/db/repositories/articles.py::ArticlesRepository]]. `is_article_favorited_by_user` delegates to the query layer and returns the boolean result directly, while `add_article_into_favorites` and `remove_article_from_favorites` respectively persist and delete the favorite relationship between a user and an article [[target/app/db/repositories/articles.py::ArticlesRepository]].

## ArticlesRepository

`ArticlesRepository` is the data-access class responsible for all database operations relating to articles, and it inherits from `BaseRepository` [[target/app/db/repositories/articles.py::ArticlesRepository]] [[target/app/db/repositories/base.py::BaseRepository]]. It is not a Pydantic model. The class carries a `# noqa: WPS214` suppression, indicating it deliberately contains a higher-than-usual number of methods [[target/app/db/repositories/articles.py::ArticlesRepository]].

On construction, it forwards the database connection to its parent class and then creates two collaborating repositories — a `ProfilesRepository` and a `TagsRepository` — both sharing the same connection, so that article-level operations can delegate profile and tag lookups without opening separate connections [[target/app/db/repositories/articles.py::ArticlesRepository::__init__]].

The private `_get_article_from_db_record` helper assembles a fully populated `Article` domain object from a raw database row, reading scalar fields directly from the row while accepting `slug` and `author_username` as separate parameters [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. It fetches the author profile (forwarding a `requested_user` so follow state is reflected), retrieves associated tags and favorites count, and resolves the `favorited` flag only when a `requested_user` is present, defaulting to `False` otherwise [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]].

The private `_link_article_with_tags` helper associates a sequence of tag strings with an article identified by its slug, writing one `{slug, tag}` mapping per tag through `queries.add_tags_to_article` [[target/app/db/repositories/articles.py::ArticlesRepository::_link_article_with_tags]].

`create_article` persists a new article and its tags atomically inside a transaction — inserting the article row, ensuring all tags exist, linking them, and then hydrating a full `Article` domain object outside the transaction boundary before returning it [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. `update_article` deep-copies the existing `Article`, overlays any supplied field replacements, executes `queries.update_article` within a transaction using the original slug and author as lookup keys, and returns the modified copy [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]]. `delete_article` removes an article row from the database within a transaction, keyed by slug and author username [[target/app/db/repositories/articles.py::ArticlesRepository::delete_article]].

`get_article_by_slug` fetches a single article row by slug and hydrates it into a domain object, raising `EntityDoesNotExist` if no matching row is found [[target/app/db/repositories/articles.py::ArticlesRepository::get_article_by_slug]]. `filter_articles` builds a dynamic pypika query against the articles table — optionally joining on tags, author, or favorites — and returns a paginated list of hydrated `Article` objects, personalised for the `requested_user` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. `get_articles_for_user_feed` queries for articles written by authors the requesting user follows, hydrating each raw row into a full `Article` before returning the list [[target/app/db/repositories/articles.py::ArticlesRepository::get_articles_for_user_feed]].

The remaining methods handle tag and favorites data. `get_tags_for_article_by_slug` retrieves all tags for an article by slug, returning them as a flat list of strings [[target/app/db/repositories/articles.py::ArticlesRepository::get_tags_for_article_by_slug]]. `get_favorites_count_for_article_by_slug` returns the integer count of how many users have favorited a given article [[target/app/db/repositories/articles.py::ArticlesRepository::get_favorites_count_for_article_by_slug]]. `is_article_favorited_by_user` delegates to the query layer and returns the boolean result of the `"favorited"` key directly [[target/app/db/repositories/articles.py::ArticlesRepository::is_article_favorited_by_user]]. `add_article_into_favorites` persists a favorite relationship between a user and an article, returning nothing on success [[target/app/db/repositories/articles.py::ArticlesRepository::add_article_into_favorites]], and `remove_article_from_favorites` deletes that relationship using the same connection, username, and slug parameters [[target/app/db/repositories/articles.py::ArticlesRepository::remove_article_from_favorites]].

### __init__

Initialises the repository by forwarding the database connection to the parent class via `super().__init__` [[target/app/db/repositories/articles.py::ArticlesRepository::__init__]], then constructs and stores a `ProfilesRepository` and a `TagsRepository`, both sharing the same connection, as collaborators available to the article-level operations of `ArticlesRepository` [[target/app/db/repositories/articles.py::ArticlesRepository::__init__]].

### _get_article_from_db_record

Assembles and returns a fully populated `Article` domain object from a raw database record and supplementary async lookups [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. Scalar fields (`id_`, `title`, `description`, `body`, `created_at`, `updated_at`) are read directly from `article_row`, while `slug` and `author_username` are passed in separately rather than extracted from the row [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. The author profile is fetched via `self._profiles_repo.get_profile_by_username`, forwarding `requested_user` so the profile can reflect follow state [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. Tags are retrieved with `self.get_tags_for_article_by_slug` and the favorites count with `self.get_favorites_count_for_article_by_slug`, both keyed by `slug` [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. The `favorited` field is resolved by calling `self.is_article_favorited_by_user` only when `requested_user` is not `None`; otherwise it is hardcoded to `False` [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]].

### _link_article_with_tags

Associates a set of tag strings with an article by its slug, calling `queries.add_tags_to_article` with the shared database connection and a list of `{slug, tag}` mappings — one entry per tag in the provided sequence [[target/app/db/repositories/articles.py::ArticlesRepository::_link_article_with_tags]]. It is a private async helper on `ArticlesRepository`, intended to be called internally after an article record has been created or updated [[target/app/db/repositories/articles.py::ArticlesRepository]].

### add_article_into_favorites

Persists a favorite relationship between a user and an article by delegating to `queries.add_article_to_favorites` with the repository's active connection, the user's username, and the article's slug [[target/app/db/repositories/articles.py::ArticlesRepository::add_article_into_favorites]]. It is a method of [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) and returns nothing on success [[target/app/db/repositories/articles.py::ArticlesRepository::add_article_into_favorites]].

### create_article

Persists a new article to the database within a transaction, then returns a fully hydrated `Article` domain object [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. The transaction wraps both the article insert and any tag operations so they succeed or fail atomically [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. It inserts the article row by delegating to `queries.create_new_article`, passing the connection along with all scalar fields plus `author.username` [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. When `tags` is non-empty, it first ensures all tags exist via `self._tags_repo.create_tags_that_dont_exist`, then associates them with the new article via `self._link_article_with_tags` [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. After the transaction commits, `self._get_article_from_db_record` is called outside the transaction boundary to assemble and return the final `Article`, using the author as the `requested_user` [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]].

### delete_article

Permanently deletes the given article from the database by executing `queries.delete_article` with the article's slug and author username, scoped inside a database transaction to ensure atomicity [[target/app/db/repositories/articles.py::ArticlesRepository::delete_article]]. It is a method of `ArticlesRepository` and accepts a single keyword-only argument, the `Article` instance to remove [[target/app/db/repositories/articles.py::ArticlesRepository]] [[target/app/db/repositories/articles.py::ArticlesRepository::delete_article]].

### filter_articles

Retrieves a filtered, paginated list of articles from the database, returning up to `limit` articles (default 20) starting at `offset` (default 0) [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. It builds a dynamic pypika `Query` against the `articles` table, embedding a correlated subquery that resolves the author's username via the `users` table using positional `Parameter` placeholders for asyncpg [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. When `tag` is supplied, the query is extended with a JOIN on `articles_to_tags` whose ON clause contains a subquery matching the tag value against the `tags` table [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. When `author` is supplied, a JOIN on `users` is added, filtered by a subquery that looks up the user's `id` by username [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. When `favorited` is supplied, a JOIN on `favorites` is added, again using a username-to-id subquery against `users` to find whose favorites to match [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. All filter values are accumulated in `query_params` and appended with positional indices that increment per optional filter; `limit` and `offset` are always appended last as the final two parameters [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. The final SQL is executed via `self.connection.fetch`, and each raw row is converted to an `Article` domain object by `self._get_article_from_db_record`, which also receives the `requested_user` for personalisation such as favourite and follow state [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

### get_article_by_slug

Fetches a single article from the database by its slug, delegating the query to `queries.get_article_by_slug` with the active connection [[target/app/db/repositories/articles.py::ArticlesRepository::get_article_by_slug]]. If a matching row is found, it is hydrated into a full `Article` domain object via `self._get_article_from_db_record`, passing through the slug, author username, and the optional `requested_user` (which controls user-relative data such as favouriting state) [[target/app/db/repositories/articles.py::ArticlesRepository::get_article_by_slug]]. If no row is returned, it raises `EntityDoesNotExist` with a message identifying the missing slug [[target/app/db/errors.py::EntityDoesNotExist]].

> **Raises:** EntityDoesNotExist

### get_articles_for_user_feed

Fetches a paginated list of articles written by authors that `user` follows, querying the database via `queries.get_articles_for_feed` with the follower's username, `limit` (default 20), and `offset` (default 0) [[target/app/db/repositories/articles.py::ArticlesRepository::get_articles_for_user_feed]]. Each raw database row is then hydrated into a full `Article` domain object by calling `self._get_article_from_db_record`, passing the row, its slug, its author's username, and the requesting user for personalised fields such as favouriting state [[target/app/db/repositories/articles.py::ArticlesRepository::get_articles_for_user_feed]]. The method is `async` and all per-row hydration calls are also awaited, so the entire list is resolved before returning [[target/app/db/repositories/articles.py::ArticlesRepository]].

### get_favorites_count_for_article_by_slug

Accepts a slug string and queries the database for the total number of times the corresponding article has been favourited, returning the integer extracted from the `favorites_count` key of the query result [[target/app/db/repositories/articles.py::ArticlesRepository::get_favorites_count_for_article_by_slug]]. It is an `async` method on [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) and delegates all data access to `queries.get_favorites_count_for_article`, passing the repository's connection alongside the slug [[target/app/db/repositories/articles.py::ArticlesRepository::get_favorites_count_for_article_by_slug]].

### get_tags_for_article_by_slug

Accepts a keyword-only `slug` argument and queries the database via `queries.get_tags_for_article_by_slug`, passing the repository's connection and the slug, to retrieve all tag rows associated with that article [[target/app/db/repositories/articles.py::ArticlesRepository::get_tags_for_article_by_slug]]. It then extracts the `"tag"` field from each returned row and returns them as a flat list of strings [[target/app/db/repositories/articles.py::ArticlesRepository::get_tags_for_article_by_slug]].

### is_article_favorited_by_user

Async method on [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) that checks whether a given article is favorited by a specific user [[target/app/db/repositories/articles.py::ArticlesRepository::is_article_favorited_by_user]]. It delegates to `queries.is_article_in_favorites`, passing the repository's active connection alongside the user's username and the article slug [[target/app/db/repositories/articles.py::ArticlesRepository::is_article_favorited_by_user]]. The raw query result's `"favorited"` key is extracted and returned directly as the `bool` answer [[target/app/db/repositories/articles.py::ArticlesRepository::is_article_favorited_by_user]].

### remove_article_from_favorites

Removes an article from a user's favorites by delegating to `queries.remove_article_from_favorites` with the repository's active database connection, the user's username, and the article's slug [[target/app/db/repositories/articles.py::ArticlesRepository::remove_article_from_favorites]]. It is a keyword-only async method on [[target/app/db/repositories/articles.py::ArticlesRepository]] and produces no return value [[target/app/db/repositories/articles.py::ArticlesRepository::remove_article_from_favorites]].

### update_article

Accepts an `Article` object together with optional replacement values for `slug`, `title`, `body`, and `description`, then produces a deep copy of the article via `article.copy(deep=True)` and applies each provided value over the copy's corresponding field, falling back to the original value when a parameter is `None` [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]]. Inside a database transaction opened through `self.connection.transaction()`, it calls `queries.update_article` with the original slug and author username as lookup keys and the new field values as replacements, storing the returned timestamp in `updated_article.updated_at` [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]]. The updated `Article` copy is then returned to the caller [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]].
