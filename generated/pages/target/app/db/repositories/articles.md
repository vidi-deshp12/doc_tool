# articles

This module is the data-access layer for all article-related database operations in the application [[target/app/db/repositories/articles.py]]. It defines a single class, `ArticlesRepository`, which inherits from `BaseRepository` and centralises every interaction with the articles table — creation, retrieval, filtering, updating, deletion, and favourites management [[target/app/db/repositories/articles.py::ArticlesRepository]].

The class is initialised with an asyncpg `Connection` object that is forwarded to the parent class for shared infrastructure, while two collaborating repositories — `ProfilesRepository` and `TagsRepository` — are instantiated on the same connection and stored as `self._profiles_repo` and `self._tags_repo` [[target/app/db/repositories/articles.py::ArticlesRepository]]. This design means the class carries no independently declared data fields beyond that inherited connection and the two sub-repository references [[target/app/db/repositories/articles.py::ArticlesRepository]].

On the write side, `create_article` persists a new article row inside a database transaction, optionally upserts any supplied tags through `_tags_repo`, attaches them to the article via the private `_link_article_with_tags` helper, and then hydrates a full `Article` domain object from the returned raw row [[target/app/db/repositories/articles.py::ArticlesRepository]]. `update_article` deep-copies the existing `Article`, applies whichever optional field overrides were provided among `slug`, `title`, `body`, and `description`, runs the update inside a transaction, and returns the copy with `updated_at` set to the timestamp the database echoes back [[target/app/db/repositories/articles.py::ArticlesRepository]]. `delete_article` wraps row removal in a transaction, keying the lookup on the article's slug and author username [[target/app/db/repositories/articles.py::ArticlesRepository]]. `add_article_into_favorites` and `remove_article_from_favorites` each delegate directly to a named query, translating the `Article` and `User` domain objects into the slug and username identifiers the query layer requires [[target/app/db/repositories/articles.py::ArticlesRepository]].

On the read side, `get_article_by_slug` fetches a single raw row by slug and raises `EntityDoesNotExist` when none is found, otherwise forwarding the row to the private assembly helper [[target/app/db/repositories/articles.py::ArticlesRepository]]. `filter_articles` dynamically builds a pypika query, conditionally joining `articles_to_tags`, `users`, and `favorites` when the `tag`, `author`, and `favorited` arguments are respectively supplied, and appends `limit` and `offset` as positional asyncpg parameters before converting each result row into an `Article` [[target/app/db/repositories/articles.py::ArticlesRepository]]. `get_articles_for_user_feed` retrieves articles authored by users that the requesting user follows, paginating with `limit` and `offset` and hydrating each row in the same manner [[target/app/db/repositories/articles.py::ArticlesRepository]]. `get_tags_for_article_by_slug` returns a plain list of tag strings for a given slug, while `get_favorites_count_for_article_by_slug` returns the integer favourite count, and `is_article_favorited_by_user` returns a boolean indicating whether a specific user has favourited a specific article [[target/app/db/repositories/articles.py::ArticlesRepository]].

Two private helpers underpin all of the above. `_get_article_from_db_record` is the central assembly point: it reads scalar fields from the raw database `Record` and then issues additional async calls to fetch the author's profile with follow-state, the article's tags, the favourites count, and — only when a `requested_user` is present — the per-user favourited flag, defaulting to `False` for unauthenticated callers [[target/app/db/repositories/articles.py::ArticlesRepository]]. `_link_article_with_tags` constructs a list of `{slug, tag}` dictionaries and forwards it to the named query `add_tags_to_article`, serving exclusively as an internal helper for write paths that need to associate tags with an article [[target/app/db/repositories/articles.py::ArticlesRepository]].

## ArticlesRepository

`ArticlesRepository` is the data-access class responsible for all database operations involving articles, spanning creation, retrieval, filtering, updating, deletion, and favourites management [[target/app/db/repositories/articles.py::ArticlesRepository]]. It is not a Pydantic model; it is a plain Python class that inherits from [`BaseRepository`](target/app/db/repositories/base.py::BaseRepository), which supplies the shared database connection infrastructure used throughout [[target/app/db/repositories/base.py::BaseRepository]].

The constructor accepts a `Connection` object, passes it to the parent via `super().__init__(conn)`, and additionally instantiates two collaborating repositories — `ProfilesRepository` and `TagsRepository` — each sharing the same connection, stored as `self._profiles_repo` and `self._tags_repo` [[target/app/db/repositories/articles.py::ArticlesRepository::__init__]]. This means the class holds no independently declared data fields; its only instance state is the connection inherited from the base class and those two sub-repository references [[target/app/db/repositories/articles.py::ArticlesRepository::__init__]].

The public write surface covers four operations. `create_article` persists a new article within a database transaction, optionally upserts any supplied tags via `_tags_repo`, links them to the article via the private `_link_article_with_tags` helper, and then hydrates a full `Article` domain object from the raw row [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. `update_article` deep-copies the existing `Article`, applies whichever of the four optional field overrides (`slug`, `title`, `body`, `description`) were provided, executes the update inside a transaction, and returns the copy with its `updated_at` field set to the timestamp returned by the database [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]]. `delete_article` wraps the removal of the article row in a transaction, using the article's slug and author username as lookup keys [[target/app/db/repositories/articles.py::ArticlesRepository::delete_article]]. `add_article_into_favorites` and `remove_article_from_favorites` each delegate directly to the corresponding named query, translating the `Article` and `User` domain objects into the slug and username identifiers the query layer expects [[target/app/db/repositories/articles.py::ArticlesRepository::add_article_into_favorites]] [[target/app/db/repositories/articles.py::ArticlesRepository::remove_article_from_favorites]].

The public read surface covers five operations. `get_article_by_slug` fetches a single raw row by slug and raises `EntityDoesNotExist` if none is found, otherwise delegating to the private assembly helper [[target/app/db/repositories/articles.py::ArticlesRepository::get_article_by_slug]]. `filter_articles` dynamically builds a pypika query, conditionally joining `articles_to_tags`, `users`, and `favorites` when the `tag`, `author`, and `favorited` filter arguments are respectively supplied, appending `limit` and `offset` as positional asyncpg parameters, and converting each resulting row into an `Article` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. `get_articles_for_user_feed` queries for articles authored by users that the requesting user follows, paginating with `limit` and `offset` and hydrating each row in the same manner [[target/app/db/repositories/articles.py::ArticlesRepository::get_articles_for_user_feed]]. `get_tags_for_article_by_slug` returns a plain `List[str]` extracted from the tag rows for a given slug [[target/app/db/repositories/articles.py::ArticlesRepository::get_tags_for_article_by_slug]]. `get_favorites_count_for_article_by_slug` returns an `int` by querying the database and extracting the `"favorites_count"` field [[target/app/db/repositories/articles.py::ArticlesRepository::get_favorites_count_for_article_by_slug]]. `is_article_favorited_by_user` returns a `bool` indicating whether a specific user has favourited a specific article, delegating to a named query and extracting the `"favorited"` key [[target/app/db/repositories/articles.py::ArticlesRepository::is_article_favorited_by_user]].

Two private helpers support the public API. `_get_article_from_db_record` is the central assembly point: it reads scalar fields directly from the raw database `Record`, then performs additional async calls to fetch the author's profile (with follow-state relative to `requested_user`), the article's tags, the favourites count, and — only when `requested_user` is present — the per-user favourited flag, defaulting to `False` for unauthenticated callers [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. `_link_article_with_tags` constructs a list of `{slug, tag}` dictionaries and passes it to `queries.add_tags_to_article`, serving exclusively as an internal helper for write operations that need to associate tags with an article [[target/app/db/repositories/articles.py::ArticlesRepository::_link_article_with_tags]].

### _get_article_from_db_record

`_get_article_from_db_record` is an async helper method on [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) that assembles and returns a fully populated `Article` domain object from a raw database record and a set of supplementary inputs [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]].

It accepts keyword-only arguments: `article_row`, a low-level `Record` containing the article's raw database fields; `slug`, the article's URL-friendly identifier; `author_username`, the string username of the article's author; and `requested_user`, an optional `User` representing the currently authenticated caller, which may be `None` [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]].

Scalar fields — `id`, `title`, `description`, `body`, `created_at`, and `updated_at` — are read directly from `article_row` [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. The remaining fields require async I/O: the author profile is fetched by awaiting `self._profiles_repo.get_profile_by_username`, passing `author_username` and `requested_user` so that follow-relationship state is included in the profile [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. The article's tags are retrieved by awaiting `self.get_tags_for_article_by_slug`, and the total number of favourites is retrieved by awaiting `self.get_favorites_count_for_article_by_slug` [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. The `favorited` flag is set by awaiting `self.is_article_favorited_by_user` only when `requested_user` is present; otherwise it defaults to `False`, making the method safe to call from unauthenticated contexts [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]].

The method returns the constructed `Article` instance directly, making it a private assembly point that other methods in [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) can delegate to whenever they need to convert a raw row into a rich domain object [[target/app/db/repositories/articles.py::ArticlesRepository]].

### create_article

`create_article` is an asynchronous method on [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) that persists a new article to the database and returns a fully hydrated [`Article`](target/app/db/repositories/articles.py::ArticlesRepository::create_article) domain object. It accepts only keyword arguments — `slug`, `title`, `description`, `body`, a `User` instance as `author`, and an optional sequence of tag strings — making the call site explicit and resistant to argument-order mistakes [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]].

The write work runs inside a database transaction opened via `self.connection.transaction()`, so that the article row and its tag associations are committed atomically or rolled back together [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. Within that transaction, `queries.create_new_article` is called first, inserting the article record and returning the raw database row [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. If any tags were supplied, the method delegates to `self._tags_repo.create_tags_that_dont_exist` to upsert any previously unseen tags, and then calls `self._link_article_with_tags` to associate those tags with the newly created article's slug — both calls happen inside the same transaction [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]].

After the transaction closes, `self._get_article_from_db_record` is called outside the transaction boundary to build and return the `Article` domain object from the raw row, passing the author's username extracted from the row and the `author` object as the requesting user [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. ### filter_articles

`filter_articles` is an asynchronous method on the [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) class that queries the database for a filtered, paginated list of articles and returns them as `List[Article]` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

All parameters are keyword-only: `tag`, `author`, and `favorited` are optional strings that narrow the result set, while `limit` (default 20) and `offset` (default 0) control pagination, and `requested_user` is an optional `User` whose identity is forwarded to per-record enrichment [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

The method builds a SQL query dynamically using pypika's `Query.from_` builder, starting with a base `SELECT` over the `articles` table that includes all core article columns plus a correlated subquery that fetches the author's username from the `users` table, aliased as `AUTHOR_USERNAME_ALIAS` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. Positional parameters are tracked with a running counter (`query_params_count`) so that each `Parameter(n)` call emits the correct `$n` placeholder for asyncpg [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

When `tag` is provided, the query is extended with a JOIN on `articles_to_tags`, filtering to rows whose tag matches a subquery against `tags_table` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. When `author` is provided, a JOIN on `users` is added, restricting to articles whose `author_id` matches the user ID returned by a subquery on `users.username` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. When `favorited` is provided, a JOIN on `favorites` is added, keeping only articles favorited by the user whose username matches a similar subquery [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

After all conditional joins are applied, `limit` and `offset` are appended to `query_params` and bound via `Parameter` placeholders using `query.limit(...).offset(...)` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. The fully constructed SQL is executed with `self.connection.fetch(query.get_sql(), *query_params)`, which returns raw database rows [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

Each raw row is then passed to `self._get_article_from_db_record`, supplying the row itself, its slug, the author username extracted from the aliased column, and the `requested_user`, and the method returns the resulting list of `Article` objects [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

### update_article
