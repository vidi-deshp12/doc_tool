# articles

This module is the dedicated data-access layer for all article-related database operations in the application [[target/app/db/repositories/articles.py]]. It defines two module-level string constants, `AUTHOR_USERNAME_ALIAS` and `SLUG_ALIAS`, used as column-name keys when reading raw query results, along with a regex constant for slug normalisation, and then defines the single class that does all the real work [[target/app/db/repositories/articles.py]].

`ArticlesRepository` is the central class in this module, responsible for creating, retrieving, filtering, updating, deleting, and favouriting articles [[target/app/db/repositories/articles.py::ArticlesRepository]]. It inherits from `BaseRepository`, which supplies the shared database connection infrastructure that every repository in the project builds on [[target/app/db/repositories/articles.py::ArticlesRepository]]. Its constructor accepts a single `asyncpg` `Connection`, forwards it to the parent, and then constructs both a `ProfilesRepository` and a `TagsRepository` on the same connection, storing them as `self._profiles_repo` and `self._tags_repo` so that all three repositories participate in the same database session for any given request [[target/app/db/repositories/articles.py::ArticlesRepository]].

On the write side, `create_article` opens a database transaction, inserts the core article row via a named query, optionally ensures all supplied tags exist and then links them to the new row, and returns a fully populated `Article` domain object [[target/app/db/repositories/articles.py::ArticlesRepository]]. `update_article` deep-copies the incoming `Article` so the original is never mutated, conditionally overwrites each of the four editable fields inside a transaction, stamps the clone with the `updated_at` value returned by the database, and returns the updated copy [[target/app/db/repositories/articles.py::ArticlesRepository]]. `delete_article` wraps a single named-query call in a transaction, identifying the row by slug and author username, and returns nothing [[target/app/db/repositories/articles.py::ArticlesRepository]].

On the read side, `get_article_by_slug` fetches a single row by URL slug and raises `EntityDoesNotExist` when no match is found [[target/app/db/repositories/articles.py::ArticlesRepository]]. `filter_articles` builds its SQL dynamically using pypika, optionally joining the `articles_to_tags`, `users`, and `favorites` tables to support tag, author, and favourited-by filters, appends `limit` and `offset` as the final positional parameters, executes the assembled query, and inflates every raw row into a full `Article` [[target/app/db/repositories/articles.py::ArticlesRepository]]. `get_articles_for_user_feed` retrieves articles written by accounts that a given user follows, with `limit` and `offset` pagination, returning them as a `List[Article]` [[target/app/db/repositories/articles.py::ArticlesRepository]]. Three narrower query methods — `get_tags_for_article_by_slug`, `get_favorites_count_for_article_by_slug`, and `is_article_favorited_by_user` — return a flat tag list, a favourite count integer, and a favourited boolean respectively, and are called internally by the assembly helper as well as being part of the public surface [[target/app/db/repositories/articles.py::ArticlesRepository]].

The favouriting mutations, `add_article_into_favorites` and `remove_article_from_favorites`, are thin async wrappers that pass the user's username and the article's slug straight through to the corresponding named queries and return nothing [[target/app/db/repositories/articles.py::ArticlesRepository]].

Two private methods underpin the rest of the class. `_get_article_from_db_record` is the shared assembly routine that all public read methods funnel through: it maps scalar columns directly from the raw `Record`, awaits the author's profile from `self._profiles_repo`, fetches the tag list and favourite count via sibling methods on this same repository, and conditionally resolves the `favorited` flag only when a requesting user is present, before constructing and returning the `Article` domain object [[target/app/db/repositories/articles.py::ArticlesRepository]]. `_link_article_with_tags` is a single-statement helper that calls the `add_tags_to_article` named query with a list of slug-and-tag dict pairs, used exclusively by `create_article` to associate a new article's tags after they have been guaranteed to exist [[target/app/db/repositories/articles.py::ArticlesRepository]].

## ArticlesRepository

`ArticlesRepository` is the central data-access class responsible for all database operations relating to articles, including their creation, retrieval, filtering, updating, deletion, and favouriting [[target/app/db/repositories/articles.py::ArticlesRepository]]. It is not a Pydantic model; it is a plain Python class [[target/app/db/repositories/articles.py::ArticlesRepository]]. It inherits from `BaseRepository`, which provides the shared database connection infrastructure that all repository classes in this project build on [[target/app/db/repositories/base.py::BaseRepository]] [[target/app/db/repositories/articles.py::ArticlesRepository]].

The constructor accepts a single `conn` argument typed as `Connection`, forwards it to the parent via `super().__init__(conn)`, and then instantiates two collaborating repositories — `ProfilesRepository` and `TagsRepository` — both constructed with the same connection, storing them as `self._profiles_repo` and `self._tags_repo` [[target/app/db/repositories/articles.py::ArticlesRepository::__init__]]. Sharing the connection across all three repositories ensures that every operation within a single request participates in the same database session [[target/app/db/repositories/articles.py::ArticlesRepository::__init__]]. The class declares no additional fields of its own beyond these two collaborator references [[target/app/db/repositories/articles.py::ArticlesRepository::__init__]].

The write side of the class covers three mutating operations. `create_article` runs inside a database transaction, inserts the core article row via a named query, optionally ensures all supplied tags exist and then links them to the new article, and finally assembles and returns a fully populated `Article` domain object [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. `update_article` deep-copies the incoming `Article` model so the original is never mutated, conditionally overwrites each of the four editable fields, persists the changes inside a transaction, stamps the returned clone with the new `updated_at` value from the database, and returns it [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]]. `delete_article` wraps its single query call in a transaction, identifying the row by the article's slug and author username, and returns `None` [[target/app/db/repositories/articles.py::ArticlesRepository::delete_article]].

The read side provides several query methods. `get_article_by_slug` fetches a single article row by its URL slug, hands it to the private assembly helper, and raises `EntityDoesNotExist` when no matching row is found [[target/app/db/repositories/articles.py::ArticlesRepository::get_article_by_slug]]. `filter_articles` constructs its SQL dynamically using pypika's query builder, optionally joining `articles_to_tags`, `users`, and `favorites` tables for tag, author, and favourited-by filters respectively, appends `limit` and `offset` as the final two positional parameters, executes the assembled query, and inflates each raw row into a full `Article` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. `get_articles_for_user_feed` retrieves articles authored by accounts that a given user follows, paginated by `limit` and `offset`, and returns them as a `List[Article]` [[target/app/db/repositories/articles.py::ArticlesRepository::get_articles_for_user_feed]]. `get_tags_for_article_by_slug` returns a flat `List[str]` of tag strings for a given article slug [[target/app/db/repositories/articles.py::ArticlesRepository::get_tags_for_article_by_slug]]. `get_favorites_count_for_article_by_slug` returns the total favourite count for an article as an `int` [[target/app/db/repositories/articles.py::ArticlesRepository::get_favorites_count_for_article_by_slug]]. `is_article_favorited_by_user` returns a `bool` indicating whether a particular user has favourited a particular article [[target/app/db/repositories/articles.py::ArticlesRepository::is_article_favorited_by_user]].

The favouriting operations are thin async wrappers. `add_article_into_favorites` accepts an `Article` and a `User` and delegates directly to the underlying query with no further transformation, returning `None` [[target/app/db/repositories/articles.py::ArticlesRepository::add_article_into_favorites]]. `remove_article_from_favorites` does the same in the opposite direction, passing the user's username and the article's slug to the corresponding delete query and returning `None` [[target/app/db/repositories/articles.py::ArticlesRepository::remove_article_from_favorites]].

Two private helpers support the public surface. `_get_article_from_db_record` is the shared assembly routine: given a raw database `Record`, a slug, an author username, and an optional requesting user, it maps scalar columns directly, awaits the author's profile from `self._profiles_repo`, fetches the tag list and favourite count via sibling methods, conditionally resolves the `favorited` flag only when a `requested_user` is present, and constructs and returns the `Article` domain object [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. `_link_article_with_tags` is a single-statement helper that calls `queries.add_tags_to_article` with a list of slug-and-tag dict pairs, associating a set of tags with a newly created article [[target/app/db/repositories/articles.py::ArticlesRepository::_link_article_with_tags]].

### _get_article_from_db_record

`_get_article_from_db_record` is a private async helper method on `ArticlesRepository` that assembles and returns a fully populated `Article` domain object from a raw database record plus supplementary query results [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]].

It accepts four keyword-only arguments: `article_row`, a `Record` holding the raw column values fetched from the database; `slug`, the article's URL-friendly identifier; `author_username`, the username of the article's author; and `requested_user`, an optional `User` representing whoever is making the request (used to personalise certain fields) [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]].

The method constructs the `Article` by mapping scalar fields — `id`, `title`, `description`, `body`, `created_at`, and `updated_at` — directly from `article_row`, while the remaining fields require their own async lookups [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. The author profile is resolved by calling `self._profiles_repo.get_profile_by_username`, forwarding both `author_username` and `requested_user` so the profile can reflect any follow relationship [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. The article's tag list is fetched via `self.get_tags_for_article_by_slug`, and its total favourite count via `self.get_favorites_count_for_article_by_slug`, both keyed on `slug` [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. The `favorited` flag is populated by calling `self.is_article_favorited_by_user` only when `requested_user` is present; otherwise it is set to `False`, preventing an unnecessary query for anonymous callers [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]].

Because every sub-query is awaited individually, the method is declared `async` and must itself be awaited by callers within `ArticlesRepository` [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]]. No decorators are applied, no exceptions are explicitly raised, and the return type is `Article` [[target/app/db/repositories/articles.py::ArticlesRepository::_get_article_from_db_record]].

### _link_article_with_tags

`_link_article_with_tags` is a private asynchronous method on [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) that associates a set of tags with an existing article identified by its slug [[target/app/db/repositories/articles.py::ArticlesRepository::_link_article_with_tags]]. It accepts two keyword-only arguments: `slug`, a `str` identifying the article, and `tags`, a `Sequence[str]` of tag strings to attach [[target/app/db/repositories/articles.py::ArticlesRepository::_link_article_with_tags]]. The method returns `None` [[target/app/db/repositories/articles.py::ArticlesRepository::_link_article_with_tags]].

Its entire body is a single `await` call to `queries.add_tags_to_article`, passing the repository's shared database connection alongside a list of row-like dicts built by pairing the slug (under `SLUG_ALIAS`) with each individual tag from the sequence [[target/app/db/repositories/articles.py::ArticlesRepository::_link_article_with_tags]]. The leading underscore in its name signals that it is an internal helper, not part of the public API of [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) [[target/app/db/repositories/articles.py::ArticlesRepository]].

### create_article

`create_article` is an asynchronous method on `ArticlesRepository` that persists a new article to the database and returns a fully populated `Article` domain object [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]].

It accepts keyword-only arguments covering the article's core fields — `slug`, `title`, `description`, `body`, and `author` — plus an optional `tags` sequence that defaults to `None` [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. The entire write path runs inside a database transaction opened via `self.connection.transaction()`, so that if any step fails the database remains unchanged [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]].

Inside that transaction, `queries.create_new_article` is called with the connection and all core fields, including `author.username` derived from the passed-in `User`, and its return value is captured as the raw database row [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. If `tags` is truthy, two further operations happen within the same transaction: `self._tags_repo.create_tags_that_dont_exist` ensures every tag string has a corresponding database record, and then `self._link_article_with_tags` associates those tags with the newly created article by its slug [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]].

Once the transaction closes, `self._get_article_from_db_record` is called outside the transaction block to construct and return the `Article` domain object from the raw row, passing the slug, the author username read back from the row, and the original `author` as the requesting user [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]]. The method is decorated with a `# noqa: WPS211` suppression, indicating the linter's "too many arguments" rule is intentionally silenced for this signature [[target/app/db/repositories/articles.py::ArticlesRepository::create_article]].

### filter_articles

`filter_articles` is an asynchronous method on [`ArticlesRepository`](target/app/db/repositories/articles.py::ArticlesRepository) that queries the database for a filtered, paginated list of articles and returns them as a `List[Article]` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

The method accepts six keyword-only optional filters — `tag`, `author`, `favorited`, `limit` (default `20`), `offset` (default `0`), and `requested_user` — all of which may be omitted, making every filter entirely optional [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

It builds its SQL dynamically using pypika's `Query` builder, starting with a base `SELECT` over the `articles` table that includes a correlated scalar subquery to resolve each article's author username via the `users` table [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. Each optional filter is applied by appending a positional parameter to `query_params` and joining an additional table: a `tag` filter joins `articles_to_tags` and checks against a subquery on the tags table; an `author` filter joins `users` and matches by username; a `favorited` filter joins `favorites` and resolves the favoriting user's id through a subquery on `users` [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. The counter `query_params_count` tracks how many positional parameters have been accumulated so far, ensuring that `limit` and `offset` are always appended as the final two parameters regardless of which filters are active [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

Once the query is fully assembled, `query.get_sql()` serialises it and `self.connection.fetch` executes it asynchronously with the collected parameters, returning raw database rows [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. Each row is then passed to `self._get_article_from_db_record`, forwarding the row's slug, resolved author username, and `requested_user`, so that every raw record is inflated into a full `Article` domain object before being returned [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]]. The `# noqa: WPS211` comment on the function signature suppresses a linter warning about the number of arguments [[target/app/db/repositories/articles.py::ArticlesRepository::filter_articles]].

### get_article_by_slug

It accepts two keyword-only parameters beyond `self`: a required `slug` string identifying the article, and an optional `requested_user` of type `Optional[User]` that defaults to `None`, allowing the caller to pass in the currently authenticated user for personalised data such as favourite status [[target/app/db/repositories/articles.py::ArticlesRepository::get_article_by_slug]].

### update_article

`update_article` is an asynchronous method on `ArticlesRepository` that applies partial updates to an existing article and persists the changes to the database, returning the updated model [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]].

It accepts the current `Article` instance as a required keyword argument alongside four optional keyword-only fields — `slug`, `title`, `body`, and `description` — each defaulting to `None` to indicate no change [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]]. The `# noqa: WPS211` comment signals that the linter's limit on the number of arguments is intentionally suppressed for this signature [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]].

The method begins by calling `article.copy(deep=True)` to produce an independent clone of the incoming model, ensuring the original object is never mutated [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]]. Each of the four fields is then conditionally overwritten on the copy using an `or` short-circuit: if the caller supplied a non-falsy value it is applied, otherwise the existing field value is preserved [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]].

The database write is wrapped in an explicit transaction opened via `self.connection.transaction()`, so the operation is atomic [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]]. Inside the transaction, `queries.update_article` is awaited with the original article's `slug` and its author's username as lookup keys, plus all four potentially-updated fields as the new values [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]]. The return value of that query call — the new `updated_at` timestamp — is written directly onto the cloned model [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]].

Finally, the fully populated clone is returned to the caller as an `Article` [[target/app/db/repositories/articles.py::ArticlesRepository::update_article]].
